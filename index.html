1. Core ABAP Programming

Kitchen analogy: ABAP is your kitchen language. Variables are ingredients, internal tables are trays of ingredients, IF statements are decisions, loops are repeated cooking steps, and methods are recipes you can reuse.

1.1 Data Objects

A data object is a memory location that holds a value. 

DATA lv_name TYPE string.
DATA lv_price TYPE decfloat34.

lv_name = 'Pizza'.
lv_price = '12.50'.

Kitchen example

A variable is like a labeled bowl: lv_price = bowl labeled "price".

Important declaration forms

DATA lv_name TYPE string.
CONSTANTS gc_currency TYPE waers VALUE 'EUR'.

DATA lv_number TYPE i VALUE 10.

DATA:
  lv_first  TYPE string,
  lv_second TYPE string.
Exam: Know the difference between DATA and CONSTANTS, and understand typing.

1.2 Elementary Types

Type Purpose
i Integer
p Packed decimal
decfloat16 Decimal floating point
decfloat34 Higher precision decimal floating point
string Dynamic character string
c Fixed-length character field
d Date
t Time
abap_bool Boolean-like value

1.3 Inline Declarations

Modern ABAP often lets the compiler infer the variable type. 

DATA(lv_name) = 'Pizza'.

DATA(lv_total) = 100 + 20.

LOOP AT lt_products INTO DATA(ls_product).
    WRITE ls_product-name.
ENDLOOP.
Know: DATA(...) creates a variable inline. FINAL(...) creates a read-only inline variable.

1.4 VALUE Operator

VALUE constructs data objects. 

DATA(lt_numbers) = VALUE TABLE OF i(
    ( 10 )
    ( 20 )
    ( 30 )
).

Kitchen example

Instead of preparing three ingredients separately, VALUE lets you prepare the whole tray at once.

1.5 COND Operator

DATA(lv_text) =
    COND string(
        WHEN lv_price > 100 THEN 'EXPENSIVE'
        WHEN lv_price > 50  THEN 'MEDIUM'
        ELSE 'CHEAP'
    ).

COND is expression-based conditional logic.

1.6 SWITCH Operator

DATA(lv_text) =
    SWITCH string(
        lv_status
        WHEN 'A' THEN 'ACTIVE'
        WHEN 'I' THEN 'INACTIVE'
        ELSE 'UNKNOWN'
    ).

1.7 String Templates

DATA(lv_name) = 'John'.

Useful additions

DATA(lv_text) =

1.13 READ TABLE

READ TABLE lt_products
    INTO DATA(ls_product)
    WITH KEY id = 10.

IF sy-subrc = 0.
    "found
ENDIF.

Modern table expressions are often cleaner:

If the row might not exist, use OPTIONAL or handle the exception appropriately.

1.14 Internal Tables

Kitchen: An internal table is a tray containing many records. Each record is one row.

Standard Table

DATA lt_products TYPE STANDARD TABLE OF ty_product.

Good general-purpose table.

Sorted Table

DATA lt_products TYPE SORTED TABLE OF ty_product
    WITH UNIQUE KEY id.

Automatically maintained in sorted order.

Hashed Table

DATA lt_products TYPE HASHED TABLE OF ty_product
    WITH UNIQUE KEY id.

Optimized for key-based access.

Table Typical strength
STANDARD General processing / index access
SORTED Sorted access / key access / ranges
HASHED Fast exact key lookup

INSERT VALUE #(

    name  = 'Pizza'

1.16 APPEND

APPEND VALUE #(
    id = 20
    name = 'Burger'

1.17 DELETE

DELETE lt_products WHERE id = 10.

1.18 FILTER

DATA(lt_food) =
    FILTER #( lt_products

1.19 FOR Expression

DATA(lt_names) =
    VALUE string_table(
        FOR ls_product IN lt_products

1.20 Exceptions

Exceptions are controlled mechanisms for reporting errors. 

TRY.

    DATA(ls_product) = lt_products[ id = 999 ].

CATCH cx_sy_itab_line_not_found INTO DATA(lx_error).

    "handle error

ENDTRY.

Kitchen

If the cook asks for ingredient #999 and it doesn't exist, the kitchen needs a controlled way to say: "That ingredient is unavailable."

2. Object-Oriented ABAP

Kitchen: A class is a recipe/template. An object is one actual dish created from that recipe. A method is a cooking operation. An interface is a contract describing what a kitchen appliance must do.

2.1 Class

CLASS lcl_pizza DEFINITION.

  PUBLIC SECTION.
    METHODS:
      set_price
        IMPORTING
          iv_price TYPE decfloat34,

      get_price
        RETURNING VALUE(rv_price) TYPE decfloat34.

  PRIVATE SECTION.
    DATA mv_price TYPE decfloat34.

ENDCLASS.

2.2 Implementation

CLASS lcl_pizza IMPLEMENTATION.

  METHOD set_price.
    mv_price = iv_price.
  ENDMETHOD.

  METHOD get_price.
    rv_price = mv_price.
  ENDMETHOD.

ENDCLASS.

2.3 Create Object

DATA(lo_pizza) = NEW lcl_pizza( ).

lo_pizza->set_price( 15 ).

DATA(lv_price) = lo_pizza->get_price( ).

2.4 Encapsulation

Encapsulation means controlling access to internal state. 

PRIVATE SECTION.

    DATA mv_price TYPE decfloat34.

Outside code cannot directly manipulate the private attribute.

Remember: Private data + public methods = controlled access.

2.5 Constructor

CLASS lcl_pizza DEFINITION.

  PUBLIC SECTION.

    METHODS constructor
      IMPORTING
        iv_name TYPE string.

  PRIVATE SECTION.

    DATA mv_name TYPE string.

ENDCLASS.

CLASS lcl_pizza IMPLEMENTATION.

  METHOD constructor.
    mv_name = iv_name.
  ENDMETHOD.

ENDCLASS.
Usage: 
DATA(lo_pizza) =
    NEW lcl_pizza( iv_name = 'Margherita' ).

2.6 Static Constructor

CLASS-METHODS class_constructor.

Runs when the class is first used.

2.7 Inheritance

A general recipe: "Pizza" Specialized recipe: "Vegetarian Pizza" 
CLASS lcl_pizza DEFINITION.

  PUBLIC SECTION.
    METHODS cook.

ENDCLASS.

CLASS lcl_vegetarian_pizza
    DEFINITION INHERITING FROM lcl_pizza.

  PUBLIC SECTION.
    METHODS cook REDEFINITION.

ENDCLASS.

2.8 Polymorphism

A parent reference can refer to a child object. 

DATA(lo_pizza) =
    NEW lcl_vegetarian_pizza( ).

DATA(lo_food) TYPE REF TO lcl_pizza.

lo_food = lo_pizza.

lo_food->cook( ).

2.9 Interfaces

An interface is like a restaurant contract: "Any delivery service must provide DELIVER()." 
INTERFACE lif_delivery.

  METHODS deliver.

ENDINTERFACE.
Implementation: 
CLASS lcl_driver
    DEFINITION.

  PUBLIC SECTION.

    INTERFACES lif_delivery.

ENDCLASS.
Implementation: 
METHOD lif_delivery~deliver.

  "delivery implementation

ENDMETHOD.

2.10 Factory Method

A factory creates objects for you instead of making callers know the concrete implementation. 

CLASS lcl_factory DEFINITION.

  PUBLIC SECTION.

    CLASS-METHODS create
      RETURNING VALUE(ro_object)
      TYPE REF TO lcl_pizza.

ENDCLASS.
Implementation: 
METHOD create.

  ro_object = NEW lcl_pizza( ).

ENDMETHOD.

2.11 Exception Classes

CLASS lcx_invalid_price
    DEFINITION
    INHERITING FROM cx_static_check.

ENDCLASS.
Raise: 
IF iv_price < 0.
    RAISE EXCEPTION TYPE lcx_invalid_price.
ENDIF.

2.12 OO Concepts to Know

Concept Meaning
Encapsulation Hide internal implementation
Inheritance Specialize an existing class
Polymorphism Same interface/reference, different implementation
Abstraction Expose what matters, hide unnecessary details
Exam: Be able to identify whether a class can access an attribute/method depending on PUBLIC, PROTECTED or PRIVATE visibility.

3. ABAP SQL & Code Pushdown

Kitchen: Without SQL pushdown: you bring 1 million potatoes into your kitchen and count them yourself. With database pushdown: you ask the warehouse: "How many potatoes are there?" The warehouse does the work and returns one number. Less data travels. Less application processing is needed.

3.1 Basic SELECT

SELECT FROM zproducts
  FIELDS id,
         name,
         price
  INTO TABLE @DATA(lt_products).

3.2 WHERE

SELECT FROM zproducts
  FIELDS id, name, price
  WHERE category = @lv_category
  INTO TABLE @DATA(lt_products).

3.3 SELECT SINGLE

SELECT SINGLE
    FROM zproducts
    FIELDS id, name, price
    WHERE id = @lv_id
    INTO @DATA(ls_product).
Do not blindly use SELECT SINGLE without a meaningful key/filter. Understand what guarantees uniqueness.

3.4 INNER JOIN

SELECT FROM zorders AS o
  INNER JOIN zcustomers AS c
    ON o~customer_id = c~id
  FIELDS
    o~id,
    o~amount,
    c~name
  INTO TABLE @DATA(lt_result).
Inner join = only plates where both ingredients exist.

3.5 LEFT OUTER JOIN

SELECT FROM zcustomers AS c
  LEFT OUTER JOIN zorders AS o
    ON c~id = o~customer_id
  FIELDS
    c~id,
    c~name,
    o~id AS order_id
  INTO TABLE @DATA(lt_result).

All customers remain, even if they have no order.

3.6 Aggregation

SELECT FROM zorders
  FIELDS
    customer_id,
    SUM( amount ) AS total_amount
  GROUP BY customer_id
  INTO TABLE @DATA(lt_totals).

3.7 COUNT

SELECT FROM zorders
  FIELDS
    customer_id,
    COUNT( * ) AS order_count
  GROUP BY customer_id
  INTO TABLE @DATA(lt_counts).

3.8 ORDER BY

SELECT FROM zproducts
  FIELDS id, name, price
  ORDER BY price DESCENDING
  INTO TABLE @DATA(lt_products).

3.9 DISTINCT

SELECT DISTINCT FROM zproducts
  FIELDS category
  INTO TABLE @DATA(lt_categories).

3.10 SQL Expressions

SELECT FROM zproducts
  FIELDS
    id,
    price,
    price * @lv_tax AS price_with_tax
  INTO TABLE @DATA(lt_result).

3.11 CASE Expression

SELECT FROM zproducts
  FIELDS
    id,
    CASE
      WHEN price > 100 THEN 'EXPENSIVE'
      WHEN price > 50  THEN 'MEDIUM'
      ELSE 'CHEAP'
    END AS category_text
  INTO TABLE @DATA(lt_result).

3.12 Host Variables

ABAP variables used inside SQL are escaped with @. 

SELECT FROM zproducts
  FIELDS *
  WHERE price > @lv_min_price
  INTO TABLE @DATA(lt_products).

3.13 Code Pushdown

Code pushdown means moving data-intensive processing to the database rather than reading huge datasets into ABAP and processing them there.

Bad: 
SELECT FROM zorders
  FIELDS *
  INTO TABLE @DATA(lt_orders).

LOOP AT lt_orders INTO DATA(ls_order).

  IF ls_order-amount > 1000.
     "process
  ENDIF.

ENDLOOP.
Better: 
SELECT FROM zorders
  FIELDS *
  WHERE amount > 1000
  INTO TABLE @DATA(lt_orders).
Best when suitable: use CDS/database-side calculations and filtering.

3.14 Performance Principles

  • Select only fields you need.
  • Filter as early as possible.
  • Avoid SELECT inside LOOP where possible.
  • Use joins instead of repeated database access when appropriate.
  • Use aggregation on the database.
  • Understand keys and indexes.
  • Use CDS for reusable semantic models.
  • Do not transfer unnecessary records.
Exam trap: "Database is faster" is not enough. The real principle is to reduce unnecessary data transfer and let the database perform suitable set-based operations.

4. ABAP Dictionary + CDS Data Modeling

Kitchen: The database table is your pantry. A CDS view is the organized menu describing which ingredients belong together and how they should be presented. Associations are relationships between ingredients. Annotations are labels telling consumers what the food means.

4.1 Database Table

A database table physically stores persistent data.

Example concept: 
ZPRODUCT
-----------------------
ID
NAME
PRICE
CATEGORY
CURRENCY
In ADT:
  1. Create an ABAP package.
  2. New → Other ABAP Repository Object.
  3. Select Database Table.
  4. Define fields.
  5. Define key.
  6. Activate.

4.2 Data Element

A data element describes the semantic meaning of a field.

A bowl may be "number". A label on the bowl says: "Customer ID". That semantic label is similar to a data element.

4.3 Structure

A structure groups fields without necessarily representing persistent database storage. 

TYPES:
  BEGIN OF ty_product,
    id       TYPE i,
    name     TYPE string,
    price    TYPE decfloat34,
  END OF ty_product.

4.4 CDS View Entity

Modern CDS modeling commonly uses CDS view entities. 

@EndUserText.label: 'Product'

define view entity ZI_Product
  as select from zproduct
{
    key id,
        name,
        price,
        category,
        currency
}

How to create

  1. ADT → New ABAP Repository Object.
  2. Select Data Definition.
  3. Choose CDS view entity template.
  4. Enter name and package.
  5. Define data source.
  6. Define fields.
  7. Activate.
SAP's CDS tooling uses data definitions for creating and activating CDS entities.

4.5 CDS Annotation

4.6 Associations

An association describes a relationship between CDS entities. 

define view entity ZI_Product
  as select from zproduct
  association [0..1] to ZI_Category as _Category
    on $projection.category = _Category.id
{
    key id,
        name,
        category,

        _Category
}
Association: "Every pizza belongs to a category." It describes the relationship without necessarily joining everything immediately.

4.7 Association Cardinality

Common examples: 
[0..1]
[1..1]
[0..*]
[1..*]
Meaning:
Cardinality Meaning
[0..1] Zero or one
[1..1] Exactly one
[0..*] Zero or many
[1..*] One or many

4.8 Path Expressions

_Category.name
This accesses data through the association. Example: 
define view entity ZI_Product
  as select from zproduct
  association [0..1] to ZI_Category as _Category
    on $projection.category = _Category.id
{
    key id,
    name,
    _Category.name as category_name
}

4.9 CDS Join

define view entity ZI_ProductCategory
  as select from zproduct as p
    inner join zcategory as c
      on p.category = c.id
{
    key p.id,
        p.name,
        c.name as category_name
}

4.10 Association vs Join

Join Association
Combines sources directly Models a relationship
Immediate relational operation Can be navigated through path expressions
Good for explicit data combination Good for reusable semantic relationships

4.17 CDS Access Control / DCL

CDS access control restricts which records a user is allowed to see.

Concept:

The exact syntax depends on the authorization scenario.
A restaurant has 1,000 ingredients, but a particular cook is allowed to see only ingredients belonging to their kitchen section.

4.18 CDS + ABAP SQL

CDS creates reusable semantic data models. ABAP SQL consumes them.

SAP describes CDS as reusable persistent data modeling, while ABAP SQL is used for individual/ad-hoc queries.

5. ABAP RESTful Application Programming Model — RAP

Kitchen: CDS = recipe/data model. Behavior definition = rules of what the kitchen allows. Behavior implementation = actual cooking logic. Service definition = which dishes are exposed to customers. Service binding = how customers can order them. Fiori/API consumer = customer.

5.1 What is RAP?

RAP is the modern transactional programming model for ABAP Cloud. It is used to build OData services, transactional applications and APIs.

RAP is based heavily on CDS entities, behavior definitions, behavior implementations and service infrastructure.

5.2 RAP Development Flow

Database Table → Root CDS Entity → Behavior Definition → Behavior Pool → Projection → Service Definition → Service Binding
SAP's current RAP learning content describes essentially this end-to-end flow.

5.3 Business Object

A RAP business object represents a business entity and its behavior.

Examples:
  • Travel
  • Travel Booking
  • Sales Order
  • Product
  • Invoice

5.4 Root Entity

define root view entity ZI_Travel
  as select from ztravel
{
    key travel_id,
        agency_id,
        customer_id,
        begin_date,
        end_date,
        booking_fee
}

5.5 Behavior Definition

Concept: 
managed implementation in class zbp_i_travel unique;

define behavior for ZI_Travel
persistent table ztravel
lock master
authorization master
{
    create;
    update;
    delete;
}
This says: the entity supports create/update/delete and uses managed RAP behavior.

5.6 Managed vs Unmanaged

Managed Unmanaged
RAP framework handles standard persistence. Developer controls persistence logic.
Less custom code. Useful when existing persistence logic must be reused.
Preferred for standard CRUD scenarios. Useful for special/legacy scenarios.

5.7 CRUD

create;
update;
delete;
Read operations are represented by the CDS data model/query side.

5.8 Actions

An action represents a business operation beyond normal CRUD.

Example: 
action cancelTravel result [1] $self;
Meaning: the consumer can explicitly request a business operation called cancelTravel.

5.9 Action Implementation

Concept: 
METHOD cancelTravel.

  "business logic

ENDMETHOD.

5.10 Determination

A determination automatically calculates or fills data when certain business events occur.

Kitchen:

When someone adds flour, the recipe automatically calculates the required water amount.

Concept: 
determination calculateTotal on modify
{
    field quantity;
}

5.11 Validation

A validation checks whether data is acceptable.

Example: 
validation validateDates on save
{
    create;
    update;
}
Concept: 
IF begin_date > end_date.
    "report error
ENDIF.
Remember: Validation = check whether data is valid. Determination = calculate/set data. Action = explicit business operation requested by consumer.

5.12 Feature Control

Feature control dynamically determines whether an operation/field is enabled or disabled.

Examples:
  • Button enabled only for active records.
  • Field editable only in a particular status.
  • Delete disabled after approval.

5.13 Authorization Control

Authorization determines whether the user is allowed to perform operations or access data.

Important distinction:
  • Authentication = Who are you?
  • Authorization = What are you allowed to do?

5.14 Concurrency Control

Concurrency control protects data when multiple users work on the same business object.

Kitchen:

Two cooks should not unknowingly overwrite each other's recipe changes.

Know:
  • Locks
  • ETag / optimistic concurrency concepts
  • Lock master
  • Lock dependent

5.15 Composition

A composition represents a strong parent-child relationship.

Example: 
Travel
 |
 +-- Travel Item
 |
 +-- Travel Item
 |
 +-- Travel Item
CDS concept: 
composition [0..*] of ZI_TravelItem as _Items
A composition creates a hierarchical RAP business object. Know the difference between a normal association and composition.

5.16 Child Entity

Example: 
define view entity ZI_TravelItem
  as select from ztravel_item
{
    key travel_id,
    key item_id,

5.17 Draft

Draft allows a user to work on incomplete changes without immediately committing them as active business data.

Kitchen:

A chef can prepare a dish on the preparation counter before putting it on the restaurant's official menu.

Draft is important for transactional Fiori applications.

5.18 EML — Entity Manipulation Language

EML is ABAP syntax for interacting with RAP business objects.

READ ENTITIES

READ ENTITIES OF ZI_Travel
    ENTITY Travel
    ALL FIELDS WITH
    VALUE #( ( TravelID = 1 ) )
    RESULT DATA(lt_travel).

MODIFY ENTITIES

MODIFY ENTITIES OF ZI_Travel
    ENTITY Travel
    CREATE FIELDS ( CustomerID BeginDate EndDate )
    WITH VALUE #(
      (
        %cid       = '1'
        CustomerID = '100'
        BeginDate  = '2026-01-01'
        EndDate    = '2026-01-10'
      )
    )
    MAPPED DATA(mapped)
    FAILED DATA(failed)
    REPORTED DATA(reported).
Know the important result structures: 
MAPPED
FAILED
REPORTED

5.19 COMMIT ENTITIES

Concept: 
COMMIT ENTITIES
    RESPONSE OF ZI_Travel
    FAILED DATA(failed)
    REPORTED DATA(reported).
Understand that RAP transactional processing is managed by the RAP transactional engine and that direct database manipulation of RAP BO persistent data can bypass business logic. SAP specifically warns against using writable CDS mechanisms to circumvent RAP transactional logic; EML should be used for modifying RAP business object data.

5.20 Projection View

The projection exposes a subset/view of the underlying RAP business object for a particular service or consumer.

Concept: 
define root view entity ZC_Travel
  provider contract transactional_query
  as projection on ZI_Travel
{
    key TravelID,
        CustomerID,
        BeginDate,
        EndDate
}

5.21 Behavior Projection

A behavior projection determines which behavior is exposed through the projection.

Concept: 
projection;

define behavior for ZC_Travel
{
    use create;
    use update;
    use delete;
    use action cancelTravel;
}

5.22 Service Definition

The service definition decides which projection entities are exposed. 

@EndUserText.label: 'Travel Service'

define service ZUI_TRAVEL {

5.23 Service Binding

The service binding connects the service definition to a protocol and service type, such as OData.

Concept: 
OData V4 - UI
OData V4 - Web API
In ADT:
  1. Create Service Binding.
  2. Select service definition.
  3. Select binding type.
  4. Activate.
  5. Publish.
  6. Use Preview if supported.
SAP describes a service definition as the exposed data/behavior model and a service binding as the protocol-specific exposure mechanism.

5.24 RAP Managed Query

Managed query means the RAP query framework handles the database access based on the CDS model and request.

Query options such as filtering, ordering, top and skip can be handled by the framework.

SAP documents managed query as the default case and contrasts it with unmanaged query implementations.

5.25 Unmanaged Query

Used when standard framework query processing is insufficient, for example when data comes from another service or requires special application-specific processing.

Typical concept: 
IF_RAP_QUERY_PROVIDER
The implementation provides a SELECT method for processing requests. SAP documents unmanaged queries using CDS custom entities and IF_RAP_QUERY_PROVIDER.

5.26 Messages

Messages communicate errors, warnings and information from business logic to consumers.

Know the difference between:
  • Reported messages
  • Failed instances
  • Successful operations

5.27 RAP Business Events

Example: 
TravelCreated
TravelCancelled
InvoiceCreated
Consumers can react to the event. SAP's RAP learning content includes business events as an advanced RAP topic.

5.28 RAP Extensibility

6. Clean Core, ABAP Cloud & Extensibility

Kitchen: Imagine renting a professional kitchen. You are allowed to add your own equipment at approved connection points. You should not break open the walls and modify the building. That is the basic idea behind clean core: extend SAP without tightly modifying SAP's standard implementation.

6.1 What is Clean Core?

Clean core means keeping the SAP standard core stable, upgrade-friendly and minimally modified while placing custom requirements in supported extension mechanisms.

SAP describes clean-core principles around avoiding modifications, using released APIs, and using appropriate extension mechanisms.

6.2 Why?

  • Upgrade stability
  • Lower technical debt
  • Easier maintenance
  • Faster adoption of SAP innovation
  • Reduced dependency on SAP internals

6.3 ABAP Cloud

ABAP Cloud is the cloud-oriented ABAP development model with restrictions designed to support stable, upgrade-safe development.

Important concepts:
  • Released APIs
  • Cloud language version
  • ADT/Eclipse
  • RAP
  • CDS
  • Clean Core
SAP notes that ABAP Cloud enforces the cloud language version and use of released APIs through development tooling/syntax checks.

6.4 Released API

A released API is an SAP interface/artifact that SAP has formally made available for consumption under a release contract.

Exam thinking: "Can I call this SAP class/table/CDS view?" Do not answer: "It exists." Answer: "Is it released and allowed for this ABAP Cloud development context?"

6.5 API Release Contract

Release contracts communicate the intended stability and usage of development objects.

Important concepts include: 
C0
C1
The exact contract and usage depends on the object and scenario.

6.6 Developer Extensibility

Developer extensibility allows developers to implement more sophisticated extensions using released extension points and ABAP Cloud.

Examples:
  • Complex business logic
  • Frequent SQL access
  • Same-LUW extensions
  • Local BAdI implementations
SAP describes developer extensibility as using released extension points within the ABAP Cloud development model.

6.7 Key User Extensibility

Designed for business/key users through supported SAP tools rather than traditional pro-code development.

Examples can include:
  • Custom fields
  • Custom logic where supported
  • UI adaptations

6.8 Side-by-Side Extensibility

Build an extension outside the SAP S/4HANA core, commonly on SAP BTP.

Restaurant example: The main restaurant stays untouched. You open a separate catering kitchen next door. It communicates through official doors/APIs.

6.9 On-Stack vs Side-by-Side

On-stack Side-by-side
Runs within SAP system Runs outside core, commonly BTP
Can operate in same logical unit of work More decoupled
Good for tightly integrated extensions Good for independent applications

6.10 BAdI

Business Add-In is an extension mechanism that allows custom behavior at predefined extension points.

Concept: 
SAP standard code
       |
       v
   BAdI call
       |
       v
Customer implementation
The key idea: you implement an SAP-provided extension point instead of modifying SAP standard code.

6.11 Classic Modification

A modification directly changes SAP standard objects. This creates upgrade and maintenance problems.

For modern clean-core development: avoid modifications when supported extension mechanisms exist.

6.12 Classical User Exit

Older SAP systems used various exits and enhancement techniques. Understand them mainly to recognize legacy architecture and migration challenges.

6.13 Custom Code Migration

Typical process:
  1. Inventory custom code.
  2. Identify what is actually used.
  3. Analyze dependencies.
  4. Check API release status.
  5. Remove unused code.
  6. Adapt incompatible code.
  7. Replace modifications with supported extensions.
  8. Test.
  9. Monitor.

6.14 ATC

ABAP Test Cockpit performs static checks.

It can detect:
  • Syntax/design issues
  • Performance problems
  • Cloud compatibility issues
  • Forbidden/restricted API usage
  • Quality problems

6.15 ABAP Call Monitor

Used to understand which custom code is actually executed. This is useful during custom-code analysis and migration.

6.16 SQL Monitor

Helps identify SQL statements and database access patterns, especially when analyzing performance and custom code usage.

6.17 Extensibility Decision

When given a requirement, ask:
  1. Can standard SAP functionality solve it?
  2. Can configuration solve it?
  3. Can key-user extensibility solve it?
  4. Can developer extensibility solve it?
  5. Should it be side-by-side?
  6. Is there a released API?
  7. Is there a released extension point?
  8. Will this remain upgrade-safe?

6.18 Clean Core Exam Traps

Trap 1: "Use a modification because it is easiest." Wrong direction. Trap 2: "Any SAP class is available in ABAP Cloud." Wrong. Trap 3: "Side-by-side is always the answer." Not necessarily. Some tightly integrated use cases belong on-stack. Trap 4: "Cloud means no custom code." Wrong. Cloud means custom code must follow supported architecture.

7. Code Quality, Testing & Analysis

7.1 Clean ABAP

Write code that is easy to understand, test and maintain.

Bad: 
IF x = 1.
  a = 2.
ENDIF.
Better: 
IF is_customer_active( ).
    activate_customer( ).
ENDIF.
The second version expresses intent.

7.2 ABAP Unit

ABAP Unit is the built-in unit testing framework for ABAP.

Basic structure: 
CLASS ltcl_test DEFINITION
    FOR TESTING
    DURATION SHORT
    RISK LEVEL HARMLESS.

  PRIVATE SECTION.

    METHODS test_addition FOR TESTING.

ENDCLASS.
Implementation: 
CLASS ltcl_test IMPLEMENTATION.

  METHOD test_addition.

    DATA(lv_result) = 2 + 3.

    cl_abap_unit_assert=>assert_equals(
        act = lv_result
        exp = 5 ).

  ENDMETHOD.

ENDCLASS.
SAP's current ABAP Cloud documentation treats ABAP Unit as a core testing framework and also discusses test doubles for RAP/CDS and other dependencies.

7.3 Assertions

Common concepts: 
cl_abap_unit_assert=>assert_equals
cl_abap_unit_assert=>assert_true
cl_abap_unit_assert=>assert_false
assert_bound
assert_not_bound

7.4 Arrange — Act — Assert

A good unit test often follows: 

ARRANGE
   Prepare data

ACT
   Call code

ASSERT
   Verify result

7.5 Test Doubles

A test double replaces a real dependency during testing.

Instead of testing with a real supplier, use a fake supplier that always delivers exactly the ingredients you want for the test.
Know the idea of:
  • Mock
  • Stub
  • Fake
  • Test seam/dependency isolation

7.6 ATC

ABAP Test Cockpit performs static analysis.

Know that ATC can identify problems before runtime.

7.7 Runtime Analysis

Runtime analysis helps determine where application execution spends time.

Use it when:
  • Code is unexpectedly slow.
  • A loop is expensive.
  • Method calls dominate runtime.

7.8 SQL Performance Analysis

When database access is slow, inspect SQL behavior.

Look for:
  • Too many database calls
  • Large result sets
  • Missing filtering
  • Unnecessary SELECTs
  • SELECT inside LOOP

7.9 Documentation

Modern code should explain business intent rather than obvious syntax.

Bad: 
"Add 1
lv_x = lv_x + 1.
Better: 
"Increase the retry counter after a failed payment request.
lv_retry_count += 1.

7.10 AI / Joule Awareness

Modern SAP development increasingly includes AI-assisted development. If your current C_ABAPD version includes AI-assisted development content, understand that generated code must still be reviewed, tested and validated by the developer.

AI-generated ABAP is not automatically correct. Developer responsibility remains: review → test → security check → performance check → maintainability check.

ZTRAVEL

Step 1 — Database

Create ZTRAVEL.

Step 2 — Root CDS

define root view entity ZI_Travel
  as select from ztravel
{
    key travel_id,
        customer_id,
        begin_date,
        end_date,
        status,
        price,
        currency
}

Step 3 — Behavior

managed implementation in class zbp_i_travel unique;

define behavior for ZI_Travel
persistent table ztravel
lock master
authorization master
{
    create;
    update;
    delete;

    action cancel;

    validation validate_dates on save
    {
        create;
        update;
    }
}

Step 4 — Behavior Implementation

METHOD validate_dates.

  "Check that begin date is not after end date.

ENDMETHOD.

METHOD cancel.

  "Set travel status to cancelled.

ENDMETHOD.

Step 5 — Projection

define root view entity ZC_Travel
  as projection on ZI_Travel
{
    key travel_id,
        customer_id,
        begin_date,
        end_date,
        status,
        price,
        currency
}

Step 6 — Behavior Projection

projection;

define behavior for ZC_Travel
{
    use create;
    use update;
    use delete;
    use action cancel;
}

}

11. Recommended Learning Order

  1. Modern ABAP syntax
    Variables → expressions → internal tables → exceptions.
  2. Object-Oriented ABAP
    Classes → interfaces → inheritance → polymorphism.
  3. ABAP SQL
    SELECT → JOIN → aggregation → expressions → performance.
  4. CDS
    Tables → CDS entities → associations → annotations → authorization.
  5. RAP
    BO → behavior → EML → projection → service.
  6. Clean Core
    Released APIs → extensibility → migration → upgrade safety.
  7. Testing
    ABAP Unit → test doubles → ATC → performance.
Do not reverse this order. Trying to learn RAP before understanding CDS, modern ABAP and OO ABAP usually makes RAP feel much harder than it actually is.
